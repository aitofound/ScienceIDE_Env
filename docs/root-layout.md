# Repository root layout

The repository root is an interface. Every entry at the root is either a
stable entrance for authors, agents and automation, or a namespace for records.
Anything dated, retired or historical lives under one of the named namespaces
below, never at the root.

| Path | What it holds |
| --- | --- |
| `tasks/` | The live task packages, one leaf per module at `tasks/<codebase>/<module>/`. A leaf never carries source; it names it. |
| `code/` | The pinned upstream sources, one tree per codebase at `code/<id>/`, each vendored by its own pull request before any task that builds from it. The largest directory by far and the one a solver-facing checkout needs whole. |
| `skills/` | The pointer to the authoring procedure: `package-sciaccel-task/` with a `SKILL.md` that says where the skill lives, `PIPELINE_REVISION` (the commit of the canonical repository `huangzesen/sciaccelbench-pipeline` that CI and authors run) and `scripts/sab.py`, the loader that runs the CLI from a clone at that commit. The skill text, the SPEC, the templates and the CLI are not in this repository; change the pipeline there and land the pin with its `tools/release.py`. |
| `scripts/` | Repository tooling that CI or the CLI runs today: the validator (`validate.mjs` over the shared `validate-core.mjs`), the projection generator (`gen-index.mjs`), the pass-policy fixture runner (`check-validators.py`) and the Docker build-context stager (`stage-task-source.py`). Tooling that only a retired form used moves out with that form. |
| `registry/` | Registry data: the generated `index.yaml` projection, the operator overlays (`records.yaml`, `runs.yaml`, `site.yaml`), and the two vocabularies, `fields.json` (the site's thirteen fields, byte-vendored with ScienceMysteryBench) and `arxiv-categories.json` (the optional fine-grained tags). |
| `registry.json` | The Harbor git-dataset manifest, generated by `gen-index.mjs` beside `index.yaml`. Harbor reads it at the repository root, so it stays there. |
| `runs/` | Dated execution records: products, verdicts, run receipts and the skills a submission shipped. Immutable evidence, not task definitions; a solver-facing checkout may leave it out. |
| `archive/` | Retired packages under their original slugs (`archive/sa-NNNN/`), still validated so they cannot rot, and the retired templates under `archive/templates/` with the scripts that belonged to them. |
| `docs/` | This file and `docs/history/`, the human-readable campaign records and handoffs. |
| `.github/` | Issue form, PR template, labeler and the four workflows (validate, label, label-fields, intake-index). |
| `.claude/` | A one-file redirect so Claude Code discovers the skill under `skills/`. |
| `README.md`, `AGENTS.md`, `CONTRIBUTING.md`, `LICENSE` | The entry points for humans and agents. |
| `package.json`, `package-lock.json` | The two npm dependencies the validator needs and the `check` commands CI runs. |

## Invariants

- Moving a file must not change task science, scoring, package content, or run
  evidence.
- `tasks/`, `code/`, `skills/`, `scripts/`, and `registry/` are stable public
  interfaces; do not move them merely to reduce the number of root entries.
- Retired task directories remain directly under `archive/` so their slug paths
  stay stable. Retired templates and the tooling written for them live under
  `archive/templates/<name>/` and are not active submission entry points.
- `runs/` records are immutable evidence. A path they mention may since have
  moved; the record is not edited to follow it.
- `registry.json` does not move until its external readers are audited and
  updated in the same change. The audit so far found one reader, Harbor, which
  expects it at the root.
- Prefer `git mv` plus reference updates. Never delete historical material as a
  form of tidying.
