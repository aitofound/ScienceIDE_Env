# ptmass-merger

Upstream test: `code/phantom/src/tests/test_ptmass.f90`. Policy: `pointwise`.

## The test

`run.sh <ic>` copies the pinned source, applies the unified diff of `ic/<ic>/source.patch` to the staged copy of the test source with a strict applier (every context and deleted line must match the pinned source or the run fails), builds `make SYSTEM=gfortran SETUP=testgrav phantomtest` -- serial and one goal per invocation, because build/.depends is absent upstream so `make -j` and multi-goal invocations both fail -- and runs `bin/phantomtest ptmassmerger` with OMP_NUM_THREADS pinned by SAB_THREADS. test_merger runs ten configurations of two equal-mass sinks through the merger logic of src/main/ptmass.F90: fast flybys that must not merge, slow encounters inside the unconditional radius that must, and bound pairs inside the conditional radius, followed by a thousand-step integration of a ten-sink cluster drawn from a fixed random seed in which the surviving sink count and the conserved mass and momentum are checked. run.sh then extracts the assertion lines of stdout into OUT_DIR/results.txt, dropping the banner, the epigraph, the memory report, the thread count and the wall and CPU times, and refuses to finish unless the suite reported a positive number of assertions -- a selector that matches nothing silently runs the whole suite, and a build without -DGRAVITY reports a pass with zero assertions. The full log is copied alongside for information and is not graded. Runtime knob: `SAB_THREADS` (`run.sh --help` lists it); the graded default is 1.

`run.sh altbuild` runs `ic/nominal/` on the same pinned source built with `make SYSTEM=gfortran OPENMP=yes DEBUG=yes`: Phantom's own -O0 gfortran debug build with bounds, NaN and floating-point checks instead of the nominal -O3 build. Grading never uses this third run; self-validation grades it against nominal with this check's unchanged `validate.py` and records the measured floor between the two legitimate builds.

## The two initial conditions

`ic/nominal/` holds the graded inputs. ic/variant/source.patch perturbs one binary64 initial-condition literal of the test by two ulps before the build: the velocity scale of the ten-sink cluster (test_ptmass.f90:1464, the `* 6. * vel_fac` that maps the seeded random numbers onto the range (-3,3)), from 6.0000000000000000 to 6.000000000000002. The scalars of the ten pairwise configurations are deliberately left alone: those sub-tests place the two sinks in exact antisymmetry about a fixed centre and then assert that the merged sink's velocity is exactly zero to within one ulp (tol 2.220E-16), so any perturbation at all -- including a two-ulp change of the sink mass, which was tried and measured -- pushes the residual to 4e-16 and makes the upstream test fail on the variant. The cluster branch has no such exact cancellation. The suite prints its results to four significant digits, so a two-ulp perturbation is many decades below the print resolution: the two runs print the same assertion lines with the same verdicts, and differ at most in the last digit of the entries the suite reports near zero, which are maxima over particles or over a parameter grid. That is the check's floor, and the bound is set from it. Measured: the two results.txt files are NOT byte-identical; the largest difference is 1.12e-15.

## The pass policy

The graded observable is every number the pinned unit suite prints on its own assertion lines for the ptmassmerger selector: the name and OK/FAILED verdict of each `checking ...` line, the measured error and the compiled-in tolerance it is compared against, and the closing `PASSED: n of m` tally, extracted from stdout by run.sh into results.txt after the banner, the memory report, the thread count and the wall and CPU times are dropped. Two runs are equivalent when they print the same lines in the same order with the same verdicts and every number agrees under |candidate - reference| <= 1e-13 + 2e-3|reference|. What the check exercises: the sink merger logic of src/main/ptmass.F90 over ten two-sink configurations (fast flybys that must not merge, encounters inside the unconditional radius that must, bound pairs inside the conditional radius) followed by a thousand-step integration of a ten-sink cluster drawn from the fixed seed iseed = -74205, graded on the surviving sink count and on the conserved mass and momentum. The bound is physical because the verdict is compared exactly first: the fault this check exists to catch is a port that evaluates the merge predicate on stale positions or merges the same pair twice, which changes the surviving sink count outright, and it drives at least one assertion past the tolerance src/tests holds for it -- several of those tolerances sit within a couple of per cent of the value the pinned source produces -- so the line flips from OK to FAILED and the tally falls below n of n, which no tolerance on the printed numbers can hide; the numeric bound is the second gate, and 2e-3 relative is two units in the last of the four significant digits the suite prints (the 1PE9.3 field of checkval in src/tests/testutils.f90), so a port whose error metric moves further than the print resolution is flagged even while its verdict still reads OK. It is achievable because the arithmetic is binary64 end to end (-fdefault-real-8 in build/Makefile_defaults), the test data are literals compiled into src/tests with no file or network input, and the graded run is pinned to one thread by SAB_THREADS, so two legitimate runs of the pinned source print assertion lines that agree far inside both terms. The absolute term of 1e-13 is measured rather than assumed: it governs the entries this selector prints near zero, which are maxima over particles or over a parameter grid and jitter when a sum is reordered. The calibration selfcheck of 2026-09-04 (ale-worker, x86_64 Linux, 16 cpus / 32 GB per container, Docker 29.1.3, reward 1.0) measured a nominal-versus-variant spread of 2.81e-16 over the 212 graded numbers, and the bound is a hundred times that, rounded to one significant digit; the calibration spread of 2.81e-16 leaves a margin of 356x. How far a wrong port lands is set by the suite itself rather than by a probe run: every assertion of this selector is compared in src/tests against a compiled-in tolerance that is printed on the same line and graded, the tightest here being 2.220E-16 on the merged sink position, so a port whose error crosses it flips OK to FAILED and drops the `PASSED: n of m` tally -- an exact difference that no numeric tolerance can absorb, and on the near-zero lines a stricter gate than the absolute term itself. The numeric term is the second, finer gate for a port that moves the printed error without yet failing the assertion.
