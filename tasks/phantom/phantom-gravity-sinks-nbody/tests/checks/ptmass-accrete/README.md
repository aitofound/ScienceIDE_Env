# ptmass-accrete

Upstream test: `code/phantom/src/tests/test_ptmass.f90`. Policy: `pointwise`.

## The test

`run.sh <ic>` copies the pinned source, applies the unified diff of `ic/<ic>/source.patch` to the staged copy of the test source with a strict applier (every context and deleted line must match the pinned source or the run fails), builds `make SYSTEM=gfortran SETUP=testgrav phantomtest` -- serial and one goal per invocation, because build/.depends is absent upstream so `make -j` and multi-goal invocations both fail -- and runs `bin/phantomtest ptmassaccrete` with OMP_NUM_THREADS pinned by SAB_THREADS. test_accretion drives accrete_particle in src/main/ptmass.F90 three times: two gas particles onto one sink, a whole 1000-particle disc onto the same sink, and the fast-accretion path that uses a neighbour list. Each sub-test checks the accretion and dead-particle flags and then the mass, the centre-of-mass position and velocity, the linear momentum and the angular momentum of the sink against the exact budget of what it swallowed. run.sh then extracts the assertion lines of stdout into OUT_DIR/results.txt, dropping the banner, the epigraph, the memory report, the thread count and the wall and CPU times, and refuses to finish unless the suite reported a positive number of assertions -- a selector that matches nothing silently runs the whole suite, and a build without -DGRAVITY reports a pass with zero assertions. The full log is copied alongside for information and is not graded. Runtime knob: `SAB_THREADS` (`run.sh --help` lists it); the graded default is 1.

## The two initial conditions

`ic/nominal/` holds the graded inputs. identical: the nominal and variant results.txt are byte-identical. That is the expected outcome, not a failed perturbation: the suite prints four significant digits and the perturbation is two ulps of binary64, some eleven decades below the last printed digit, so no printed number can move. The perturbation is real and does reach the arithmetic; it simply cannot reach the print. ic/variant/source.patch perturbs one binary64 initial-condition literal of the test by two ulps before the build: the smoothing length of the two gas particles that are accreted (test_ptmass.f90:960, `xyzh(4,1:2) = 0.01`), from 0.010000000000000000 to 0.010000000000000004. The masses and positions are deliberately left alone: this test asserts the sink's post-accretion position, velocity and force against hard literals (3.*pos_fac, 20.*vel_fac, 30.*acc_fac) with the tolerance tiny(0.), i.e. exact equality, and those literals are only exact for the exact mass and position literals, so a two-ulp change of the sink mass -- which was tried and measured -- makes the upstream test itself fail on the variant. The smoothing length enters none of that arithmetic. The suite prints its results to four significant digits, so a two-ulp perturbation is many decades below the print resolution: the two runs print the same assertion lines with the same verdicts, and differ at most in the last digit of the entries the suite reports near zero, which are maxima over particles or over a parameter grid. That is the check's floor, and the bound is set from it.

## The pass policy

The graded observable is every number the pinned unit suite prints on its own assertion lines for the ptmassaccrete selector: the name and OK/FAILED verdict of each `checking ...` line, the measured error and the compiled-in tolerance it is compared against, and the closing `PASSED: n of m` tally, extracted from stdout by run.sh into results.txt after the banner, the memory report, the thread count and the wall and CPU times are dropped. Two runs are equivalent when they print the same lines in the same order with the same verdicts and every number agrees under |candidate - reference| <= 1e-11 + 2e-3|reference|. What the check exercises: accrete_particle in src/main/ptmass.F90 in three configurations -- two gas particles onto one sink, a whole 1000-particle disc, and the fast-accretion path over a neighbour list -- graded on the accretion flags and on the mass, centre-of-mass position and velocity, linear momentum and angular momentum of the sink. The bound is physical because the verdict is compared exactly first: the fault this check exists to catch is a port that loses a contribution in the accretion reduction or updates the sink before all of its accreted particles are summed, which breaks the momentum budget, and it drives at least one assertion past the tolerance src/tests holds for it -- several of those tolerances sit within a couple of per cent of the value the pinned source produces -- so the line flips from OK to FAILED and the tally falls below n of n, which no tolerance on the printed numbers can hide; the numeric bound is the second gate, and 2e-3 relative is two units in the last of the four significant digits the suite prints (the 1PE9.3 field of checkval in src/tests/testutils.f90), so a port whose error metric moves further than the print resolution is flagged even while its verdict still reads OK. It is achievable because the arithmetic is binary64 end to end (-fdefault-real-8 in build/Makefile_defaults), the test data are literals compiled into src/tests with no file or network input, and the graded run is pinned to one thread by SAB_THREADS, so two legitimate runs of the pinned source print assertion lines that agree far inside both terms. The absolute term of 1e-11 is not tightened further because the calibration selfcheck of 2026-09-04 (ale-worker, x86_64 Linux, 16 cpus / 32 GB per container, Docker 29.1.3, reward 1.0) measured a nominal-versus-variant spread of exactly zero over the 49 graded numbers: there is no jitter to set a margin against, so the bound is left at the print-resolution default, and it never binds here: the entries this selector prints at or near zero. How far a wrong port lands is set by the suite itself rather than by a probe run: every assertion of this selector is compared in src/tests against a compiled-in tolerance that is printed on the same line and graded, the tightest here being tiny(0.) on the post-accretion sink position, velocity and force -- which gfortran prints as the malformed field `2.225-308`, the exponent letter squeezed out, so run.sh's number scanner reads it as the two constants 2.225 and -308; both are compiled-in literals and are graded exactly -- and 4.441E-16 on the linear momentum, so a port whose error crosses it flips OK to FAILED and drops the `PASSED: n of m` tally -- an exact difference that no numeric tolerance can absorb, and on the near-zero lines a stricter gate than the absolute term itself. The numeric term is the second, finer gate for a port that moves the printed error without yet failing the assertion.

## Evidence

Native authoring runs (Apple M1 Ultra, gfortran 15.2, 2026-09-02) measured a nominal-versus-variant spread of 0 over the 49 graded numbers.

Calibration selfcheck, the calibration host (ale-worker, x86_64 Linux, Docker 29.1.3, 16 cpus and 32 GB per container), 2026-09-04: this check passed, and the spread over the 49 graded numbers was 0 against the bound atol = 1e-11 -- no margin to compute. The two results.txt are byte-identical, which is the expected outcome: the perturbation is two ulps of binary64, eleven decades below the four significant digits the suite prints. The full record is comment/pipeline/self-validation.json, which is also where the run time and the build time live: every selfcheck regenerates them, so they are not quoted here.

How far a wrong port lands is set by the suite itself: every assertion is compared in src/tests against a compiled-in tolerance that is printed on the same graded line, so a port whose error crosses it flips OK to FAILED and drops the `PASSED: n of m` tally -- an exact difference no numeric tolerance can absorb. The tightest such tolerance in this selector is tiny(0.) on the post-accretion sink state and 4.441E-16 on the linear momentum.
