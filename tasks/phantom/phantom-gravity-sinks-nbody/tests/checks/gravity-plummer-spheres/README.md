# gravity-plummer-spheres

Upstream test: `code/phantom/src/tests/test_gravity.f90`. Policy: `pointwise`.

## The test

`run.sh <ic>` copies the pinned source, applies the unified diff of `ic/<ic>/source.patch` to the staged copy of the test source with a strict applier (every context and deleted line must match the pinned source or the run fails), builds `make SYSTEM=gfortran SETUP=testgrav phantomtest` -- serial and one goal per invocation, because build/.depends is absent upstream so `make -j` and multi-goal invocations both fail -- and runs `bin/phantomtest plummer` with OMP_NUM_THREADS pinned by SAB_THREADS. test_spheres samples ten random realisations of a Plummer sphere and of a Hernquist sphere (setplummer.f90, sampled from the tabulated cumulative mass profile) and measures the mean absolute scaled error of the tree force against the analytic profile force, so it grades the accuracy of the tree opening criterion on a realistic mass distribution rather than on a lattice. run.sh then extracts the assertion lines of stdout into OUT_DIR/results.txt, dropping the banner, the epigraph, the memory report, the thread count and the wall and CPU times, and refuses to finish unless the suite reported a positive number of assertions -- a selector that matches nothing silently runs the whole suite, and a build without -DGRAVITY reports a pass with zero assertions. The full log is copied alongside for information and is not graded. Runtime knob: `SAB_THREADS` (`run.sh --help` lists it); the graded default is 1.

## The two initial conditions

`ic/nominal/` holds the graded inputs. identical: the nominal and variant results.txt are byte-identical. That is the expected outcome, not a failed perturbation: the suite prints four significant digits and the perturbation is two ulps of binary64, some eleven decades below the last printed digit, so no printed number can move. The perturbation is real and does reach the arithmetic; it simply cannot reach the print. ic/variant/source.patch perturbs one binary64 initial-condition literal of the test by two ulps before the build: mass_total, the mass of the sampled sphere (test_gravity.f90:812, `mass_total = 1.0`), from 1.0000000000000000 to 1.0000000000000004. The suite prints its results to four significant digits, so a two-ulp perturbation is many decades below the print resolution: the two runs print the same assertion lines with the same verdicts, and differ at most in the last digit of the entries the suite reports near zero, which are maxima over particles or over a parameter grid. That is the check's floor, and the bound is set from it.

## The pass policy

The graded observable is every number the pinned unit suite prints on its own assertion lines for the plummer selector: the name and OK/FAILED verdict of each `checking ...` line, the measured error and the compiled-in tolerance it is compared against, and the closing `PASSED: n of m` tally, extracted from stdout by run.sh into results.txt after the banner, the memory report, the thread count and the wall and CPU times are dropped. Two runs are equivalent when they print the same lines in the same order with the same verdicts and every number agrees under |candidate - reference| <= 1e-11 + 2e-3|reference|. What the check exercises: the mean absolute scaled force error of the tree against the analytic profile force, over ten random realisations each of a Plummer and a Hernquist sphere. The bound is physical because the verdict is compared exactly first: the fault this check exists to catch is a port that loosens the tree opening angle or drops the quadrupole correction, which raises the mean error above the tolerance the test holds, and it drives at least one assertion past the tolerance src/tests holds for it -- several of those tolerances sit within a couple of per cent of the value the pinned source produces -- so the line flips from OK to FAILED and the tally falls below n of n, which no tolerance on the printed numbers can hide; the numeric bound is the second gate, and 2e-3 relative is two units in the last of the four significant digits the suite prints (the 1PE9.3 field of checkval in src/tests/testutils.f90), so a port whose error metric moves further than the print resolution is flagged even while its verdict still reads OK. It is achievable because the arithmetic is binary64 end to end (-fdefault-real-8 in build/Makefile_defaults), the test data are literals compiled into src/tests with no file or network input, and the graded run is pinned to one thread by SAB_THREADS, so two legitimate runs of the pinned source print assertion lines that agree far inside both terms. The absolute term of 1e-11 is not tightened further because the calibration selfcheck of 2026-09-02 (ale-worker, x86_64 Linux, 16 cpus / 32 GB per container, Docker 29.1.3, reward 1.0) measured a nominal-versus-variant spread of exactly zero over the 8 graded numbers: there is no jitter to set a margin against, so the bound is left at the print-resolution default, and it never binds here: this selector prints a single error many decades above the absolute term, no near-zero entries at all, so the absolute term never binds and the relative term and the verdict carry the check. How far a wrong port lands is set by the suite itself rather than by a probe run: every assertion of this selector is compared in src/tests against a compiled-in tolerance that is printed on the same line and graded, the tightest here being 8.500E-04 on the mean scaled force error, which the pinned source passes, so a port whose error crosses it flips OK to FAILED and drops the `PASSED: n of m` tally -- an exact difference that no numeric tolerance can absorb. The numeric term is the second, finer gate for a port that moves the printed error without yet failing the assertion. Run time 8.9 s, source build 80 s in the calibration container.

## Evidence
