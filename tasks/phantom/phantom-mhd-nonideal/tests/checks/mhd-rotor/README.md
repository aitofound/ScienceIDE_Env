# mhd-rotor

Upstream test: `code/phantom/src/setup/setup_mhdrotor.f90`. Policy: `pointwise`.

## The test

`run.sh <ic>` copies the pinned source into a scratch tree, builds `phantom` and `phantomsetup` for this SETUP, runs phantomsetup on the fixed inputs in `ic/<ic>/`, sets the window and the dump policy in the generated `.in`, evolves the problem and copies the last full dump to `OUT_DIR/final_dump`, which is the only file it writes there (the `.ev` file, `phantom.log` and the build logs stay in the work directory and are tailed to stderr on failure). Phantom SETUP=mhdrotor (MHD rotor; build/Makefile_setups), phantomsetup answering its single resolution prompt with nx = 64 (71688 particles; this setup has no .setup file), then phantom to tmax = 0.150 with dtmax = 0.010, nfulldump = 1, twallmax and dtwallmax off, on 2 OpenMP threads; 15 full dumps are written and the last one is graded. Graded defaults: This check runs the entire official configuration: nx = 64 and tmax = 0.150 with dtmax = 0.010 are exactly what src/setup/setup_mhdrotor.f90:74 and :138-139 set, and the graded run takes 106.5 s on 2 threads in the calibration container, so nothing is shortened. Measured run time 106.5 s on 2 threads in the calibration container, build excluded (165 s natively on the authoring host). mhdrotor is the only MHD setup in the tree with no .setup file, so ic/<ic>/ carries no .setup: run.sh answers phantomsetup's single resolution prompt from SAB_NX and takes every other default from 39 blank lines, as the upstream buildbot does. Every check in this task pays a full Phantom build of its own: parallel make is broken upstream (build/.depends is empty and the goals clean each other's objects) and every change of SETUP forces all 194 objects to be recompiled, so run.sh builds serially, one goal per invocation, and prints SAB_BUILD_SECONDS for the driver. The build is 100-190 s on the authoring host and 76-88 s in the calibration container (628 s for the eight checks together), and is not counted in the suite budget.

Runtime knobs (`run.sh --help`):

```
SAB_TMAX=0.150  end time of the run in code units (official 0.150); the number of steps and the runtime scale linearly with it; the default is the graded window
SAB_DTMAX=0.010  time between dumps in code units; the graded default divides SAB_TMAX so the last dump lands exactly on it
SAB_NX=64  resolution (number of particles in x); mhdrotor has no .setup file, so this is answered to phantomsetup's only prompt; npart scales as nx^3 and the runtime with it; 64 is both the source default and the graded value
SAB_NMAX=-1  cap on the number of time steps (nmax in the .in); -1 runs to SAB_TMAX (graded); a small cap exercises build, setup, run and output only
SAB_THREADS=2  OMP_NUM_THREADS for phantomsetup and phantom; the graded default. Changing it may change the order in which neighbour sums are accumulated. Cross-thread behaviour was not calibrated at the graded window, so no cross-thread determinism or equivalence result is claimed; every run must satisfy rubric.json
```

`run.sh altbuild` runs `ic/nominal/` on the same pinned source built with `make SYSTEM=gfortran OPENMP=yes DEBUG=yes`: Phantom's own -O0 gfortran debug build with bounds, NaN and floating-point checks instead of the nominal -O3 build. Grading never uses this third run; self-validation grades it against nominal with this check's unchanged `validate.py` and records the measured floor between the two legitimate builds.

## The two initial conditions

`ic/nominal/` holds only `in_overrides.txt`, because mhdrotor has no `.setup` file: every parameter of the problem is a literal in `src/setup/setup_mhdrotor.f90` and the resolution comes from `SAB_NX`. The file states the graded value of the one scalar the variant perturbs. The variant: ic/variant/in_overrides.txt raises psidecayfac from 1.000 to 1.0000000000000004 (two ulps, 1.000 * (1 + 4.4e-16)): the divergence-cleaning decay parameter of the .in. mhdrotor is the one MHD setup with no .setup file at all - every parameter is a literal in src/setup/setup_mhdrotor.f90 and the only input is the single resolution prompt - so the perturbed scalar has to live in the .in. psidecayfac sets the damping length of the psi field in the cleaning equation, it is the coefficient this particular check exists to exercise, and it is active from the first step because the rotor generates divB immediately. run.sh writes it into the .in after phantomsetup, from ic/<ic>/in_overrides.txt, because Phantom's own .in writer (src/main/utils_infiles.f90 write_inopt_real8) prints only a few digits and would truncate a frozen value.

## The pass policy

The graded observable is the state Phantom writes into the last full dump of this run - every particle array of the rotor dump at t = 0.150: x, y, z, vx, vy, vz, u, Bx, By, Bz and psi in binary64, h, alpha and divv in float32, the integer particle identifiers, and the dump's own time and particle counts as gates - compared value by value under |candidate - reference| <= 3e-11 + 1e-10|reference| for the binary64 arrays and 1e-06 + 2.4e-07|reference| for the float32 ones. In this ideal-MHD build divB and curlBx/curlBy/curlBz are excluded from grading: src/main/config.F90:221-225 sets fast_divcurlB = .true. in every build without NONIDEALMHD, and src/main/dens.F90:211-212 then accumulates them inside the density loop with a deliberate race (the source's own comment says the resulting errors are 'typically less than a percent'), so two runs of the same binary on the same host already differ there by 1e-5 to 1e-2 of the local field. What the check exercises: A dense disc spinning at v = 2 inside a uniform field is released into a static ambient medium ten times less dense, and the torsional Alfven waves it launches are followed over the setup's own official window. The initial condition is two overlapping closepacked lattices with a 10:1 density jump, so it is the module's test of SPH across a contact discontinuity, and the strong divB the rotating field generates drives the cleaning field psi to about +-0.04: this is the check where constrained hyperbolic divergence cleaning is doing real work rather than idling near zero. The bound is physical because a real implementation fault lands decades above it, and that was measured rather than asserted: this check rerun natively with alphaB = 0 in the .in (a port that drops the artificial-resistivity term of src/main/shock_capturing.f90, changing nothing else) moves the graded state by 2.1 in absolute value (largest on By), 7.2e+10 times the absolute term of this bound. The faults of the same family - dropping the magnetic tension or the anticlustering term of the SPMHD force (src/main/force.F90), integrating the induction equation without the divergence-cleaning source, losing a neighbour from the kernel sum, or computing the force loop in single precision - enter the same per-particle sums and move the state by 1e-4 to 1e-1 relative, further still. It is achievable because the whole graded state is computed and stored in binary64 (build/Makefile_defaults_gfortran sets -fdefault-real-8, and src/main/readwrite_dumps.f90 writes the positions, velocities and field as real*8) and the only arrays written in single precision are the diagnostic ones the float32 term covers, where two ulps is already 2.4e-07 relative. The floor is measured, not asserted: the pinned binary run twice on the same host with the same inputs and at the same thread count reproduces every graded array of this dump bit for bit, because each kernel sum is accumulated per particle in a private scalar and only the .ev and log reductions of src/main/energies.f90 are order-dependent, so the same-input floor at a fixed thread count is zero. Under the 5.6.0 policy, pointwise remains appropriate because the measured nominal-versus-variant sensitivity over this graded window fits comfortably inside the bound while the measured fault probe sits decades outside it. The bound is set from that spread with a margin rather than from the zero same-input floor. A different implementation or OpenMP thread count may change particle-wise summation order, but that case was not calibrated at this graded window, so no cross-thread or accelerator equivalence result is claimed: every implementation must satisfy the stated pointwise bound. The nominal-versus-variant spread, two ulps on psidecayfac, is 8.57e-14 natively (gfortran 15.2, Apple M1 Ultra, 2 threads) and 2.96e-13 in the calibration selfcheck (Debian gfortran on x86_64, ale-worker, 88 cpus, 16 declared, 2026-09-04), and the absolute term is set at 101 times the container spread. The largest float32 spread measured on this check is 4.66e-10, on alpha, under the float32 absolute term. Particle order is not part of the contract: validate.py sorts both dumps by the iorig identity array that src/main/readwrite_dumps.f90:269 writes for every particle (initialised iorig(i) = i at src/main/part.F90:741, and none of these configurations injects or accretes particles, so it is a permutation key), requires the two iorig sets to be equal, and compares every physical array in that order; a port may reorder particles for memory coalescing without failing the check. These are the finalized STOP 4 numbers, read off the calibration record in comment/pipeline/self-validation.json; if a later run shows the spread approaching them the window is shortened with the knobs, never the bound loosened.

Particle order is not part of the contract: `validate.py` sorts both dumps by the `iorig` identity array Phantom writes for every particle, requires the two `iorig` sets to be equal, and compares every physical array in that order.
Reordering the particles - for memory coalescing, for instance - therefore does not fail this check; changing any particle's state beyond the bound does.
