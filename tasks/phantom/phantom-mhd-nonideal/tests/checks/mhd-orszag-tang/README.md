# mhd-orszag-tang

Upstream test: `code/phantom/src/setup/setup_orstang.f90`. Policy: `pointwise`.

## The test

`run.sh <ic>` copies the pinned source into a scratch tree, builds `phantom` and `phantomsetup` for this SETUP, runs phantomsetup on the fixed inputs in `ic/<ic>/`, sets the window and the dump policy in the generated `.in`, evolves the problem and copies the last full dump to `OUT_DIR/final_dump`, which is the only file it writes there (the `.ev` file, `phantom.log` and the build logs stay in the work directory and are tailed to stderr on failure). Phantom SETUP=orstang (Orszag-Tang vortex; build/Makefile_setups), phantomsetup from the frozen ot.setup in ic/<ic>/ at nx = 48 (64512 particles), then phantom to tmax = 0.500 with dtmax = 0.050, nfulldump = 1, twallmax and dtwallmax off, on 2 OpenMP threads; 10 full dumps are written and the last one is graded. Graded defaults: The window is halved, tmax = 0.500 of the setup's official 1.000, keeping the official dtmax = 0.050; the resolution is reduced from the setup's nx = 128 to nx = 48. Two reasons, both measured: the graded run already takes 149.3 s on 2 threads at this window in the calibration container, and the nominal-versus-variant spread grows from 6.7e-15 at tmax = 0.100 to 2.2e-12 at tmax = 0.500 as the vortex steepens, so the full official window would put the round-off floor within reach of the bound. Measured run time 149.3 s on 2 threads in the calibration container, build excluded (222 s natively on the authoring host). Every check in this task pays a full Phantom build of its own: parallel make is broken upstream (build/.depends is empty and the goals clean each other's objects) and every change of SETUP forces all 194 objects to be recompiled, so run.sh builds serially, one goal per invocation, and prints SAB_BUILD_SECONDS for the driver. The build is 100-190 s on the authoring host and 76-88 s in the calibration container (628 s for the eight checks together), and is not counted in the suite budget.

Runtime knobs (`run.sh --help`):

```
SAB_TMAX=0.500  end time of the run in code units (official 1.000); the number of steps and the runtime scale linearly with it; the default is the graded window
SAB_DTMAX=0.050  time between dumps in code units; the graded default divides SAB_TMAX so the last dump lands exactly on it
SAB_NX=48  resolution (number of particles in x) written into ot.setup; npart scales as nx^3 and the runtime with it; official 128, graded 48
SAB_NMAX=-1  cap on the number of time steps (nmax in the .in); -1 runs to SAB_TMAX (graded); a small cap exercises build, setup, run and output only
SAB_THREADS=2  OMP_NUM_THREADS for phantomsetup and phantom; the graded default. Changing it may change the order in which neighbour sums are accumulated. Cross-thread behaviour was not calibrated at the graded window, so no cross-thread determinism or equivalence result is claimed; every run must satisfy rubric.json
```

`run.sh altbuild` runs `ic/nominal/` on the same pinned source built with `make SYSTEM=gfortran OPENMP=yes DEBUG=yes`: Phantom's own -O0 gfortran debug build with bounds, NaN and floating-point checks instead of the nominal -O3 build. Grading never uses this third run; self-validation grades it against nominal with this check's unchanged `validate.py` and records the measured floor between the two legitimate builds.

## The two initial conditions

`ic/nominal/` holds the graded `ot.setup`, exactly as `phantomsetup` writes it for this setup with the resolution set to the graded value. The variant: ic/variant/ot.setup raises bzero from 0.282094792 to 0.28209479200000009 (two ulps, 0.282094792 * (1 + 4.4e-16)): the amplitude of the initial magnetic field, which through betazero also fixes the initial pressure and density (setup_orstang.f90:96-97), so it perturbs the whole initial state at round-off and nothing else.

## The pass policy

The graded observable is the state Phantom writes into the last full dump of this run - every particle array of the ot dump at t = 0.500: x, y, z, vx, vy, vz, u, Bx, By, Bz and psi in binary64, h, alpha and divv in float32, the integer particle identifiers, and the dump's own time and particle counts as gates - compared value by value under |candidate - reference| <= 3e-10 + 1e-10|reference| for the binary64 arrays and 1e-06 + 2.4e-07|reference| for the float32 ones. In this ideal-MHD build divB and curlBx/curlBy/curlBz are excluded from grading: src/main/config.F90:221-225 sets fast_divcurlB = .true. in every build without NONIDEALMHD, and src/main/dens.F90:211-212 then accumulates them inside the density loop with a deliberate race (the source's own comment says the resulting errors are 'typically less than a percent'), so two runs of the same binary on the same host already differ there by 1e-5 to 1e-2 of the local field. What the check exercises: The Orszag-Tang vortex is the canonical ideal-MHD benchmark: a smooth periodic velocity and field configuration that steepens into interacting shocks and current sheets and then into two-dimensional MHD turbulence. Over the graded half-window it passes through the shock formation phase, so every part of the ideal-MHD path is loaded at once - the SPMHD Lorentz force, both artificial dissipation switches, the divergence cleaning and the neighbour search over 64512 particles. It is the module's heaviest and most representative workload and carries the acceleration label. The bound is physical because a real implementation fault lands decades above it, and that was measured rather than asserted: this check rerun natively with alphaB = 0 in the .in (a port that drops the artificial-resistivity term of src/main/shock_capturing.f90, changing nothing else) moves the graded state by 1.0 in absolute value (largest on the positions), 3.3e+09 times the absolute term of this bound. The faults of the same family - dropping the magnetic tension or the anticlustering term of the SPMHD force (src/main/force.F90), integrating the induction equation without the divergence-cleaning source, losing a neighbour from the kernel sum, or computing the force loop in single precision - enter the same per-particle sums and move the state by 1e-4 to 1e-1 relative, further still. It is achievable because the whole graded state is computed and stored in binary64 (build/Makefile_defaults_gfortran sets -fdefault-real-8, and src/main/readwrite_dumps.f90 writes the positions, velocities and field as real*8) and the only arrays written in single precision are the diagnostic ones the float32 term covers, where two ulps is already 2.4e-07 relative. The floor is measured, not asserted: the pinned binary run twice on the same host with the same inputs and at the same thread count reproduces every graded array of this dump bit for bit, because each kernel sum is accumulated per particle in a private scalar and only the .ev and log reductions of src/main/energies.f90 are order-dependent, so the same-input floor at a fixed thread count is zero. Under the 5.6.0 policy, pointwise remains appropriate because the measured nominal-versus-variant sensitivity over this graded window fits comfortably inside the bound while the measured fault probe sits decades outside it. The bound is set from that spread with a margin rather than from the zero same-input floor. A different implementation or OpenMP thread count may change particle-wise summation order, but that case was not calibrated at this graded window, so no cross-thread or accelerator equivalence result is claimed: every implementation must satisfy the stated pointwise bound. The nominal-versus-variant spread, two ulps on bzero, is 2.16e-12 natively (gfortran 15.2, Apple M1 Ultra, 2 threads) and 3.35e-12 in the calibration selfcheck (Debian gfortran on x86_64, ale-worker, 88 cpus, 16 declared, 2026-09-04), and the absolute term is set at 90 times the container spread. The largest float32 spread measured on this check is 0, under the float32 absolute term. This configuration is flagged chaotic: the vortex amplifies a round-off difference, and the window scan above is how the graded window was chosen, so if a calibration run ever shows the spread approaching the bound the window is shortened with SAB_TMAX rather than the bound loosened. Particle order is not part of the contract: validate.py sorts both dumps by the iorig identity array that src/main/readwrite_dumps.f90:269 writes for every particle (initialised iorig(i) = i at src/main/part.F90:741, and none of these configurations injects or accretes particles, so it is a permutation key), requires the two iorig sets to be equal, and compares every physical array in that order; a port may reorder particles for memory coalescing without failing the check. These are the finalized STOP 4 numbers, read off the calibration record in comment/pipeline/self-validation.json.

Particle order is not part of the contract: `validate.py` sorts both dumps by the `iorig` identity array Phantom writes for every particle, requires the two `iorig` sets to be equal, and compares every physical array in that order.
Reordering the particles - for memory coalescing, for instance - therefore does not fail this check; changing any particle's state beyond the bound does.

## Evidence

Same-input floor: two runs of the pinned binary with identical inputs at OMP_NUM_THREADS=2 reproduce every graded array of this dump bit for bit (Step 1 determinism table), so the same-binary floor is zero; in the ideal-MHD builds divB and curlB are the only arrays that differ, which is why they are excluded here. Reported floor: the native nominal-versus-variant measurement, 2.16e-12 over the graded binary64 arrays and 0 over the float32 ones. It was made by running this check's own run.sh for both initial conditions from the pinned code/phantom (SOURCE_DIR=code/phantom, one OUT_DIR each, SAB_* at their graded defaults) and then its own validate.py on the pair, on 2026-09-02 with gfortran 15.2 on an Apple M1 Ultra at 2 threads; verdict pass. Calibration run (sab.py task selfcheck, remote Docker host, 2026-09-04): spread 3.35e-12, run 149.3 s, build 76 s, host ale-worker.us-central1-c (Linux 6.17, x86_64, 88 cpus, docker 29.1.3; the task declares 16 cpus and 32 GB); the whole suite took 404.9 s of run time and 628 s of builds on that host, reward 1.0, eight of eight checks passed, no problems. Fault-scale probe (native, same host and method as the floor measurement, nominal versus the probe): The artificial-resistivity switch turned off (alphaB = 0 in the .in, dropping the artificial-resistivity term of src/main/shock_capturing.f90). The largest absolute difference from this check's own nominal output, over the same graded values, is 1.0 (on the positions, with the float32 divv moving by 21). Run natively on 2026-09-02 (gfortran 15.2, Apple M1 Ultra, 2 threads) with this check's own run.sh and validate.py. The native wall times were measured on a shared 20-core Apple M1 Ultra at a load average of 300-450 with three checks running concurrently and are upper bounds; expected_runtime_s is now the container measurement, and the build is excluded from the suite budget and reported separately. The bound above is the finalized STOP 4 number, set from the calibration spread with the margin the warrant states; the record is `comment/pipeline/self-validation.json` and the per-check table lives in `comment/README.md`.
