# phantomtest-derivscd

Upstream test: `code/phantom/src/tests/test_derivs.f90`. Policy: `pointwise`.

## The test

The upstream unit test of the Cullen and Dehnen (2010) artificial-viscosity switch (the selector is also spelled 'derivcullendehnen' and 'derivsswitch' in src/tests/testsuite.F90): on a uniform periodic lattice of test particles the suite calls the production derivative path src/main/deriv.F90, which runs the density loop of src/main/densityforce.F90 and the force loop of src/main/force.F90, and compares the result against analytic or independently summed values, printing a max error and the in-code tolerance for each assertion. SETUP=testkd (PERIODIC, IND_TIMESTEPS, CONST_ARTRES) is the build the survey measured as exercising about twice the number of subtests that SETUP=test does for these selectors, because the individual-timestep code paths are compiled in. This selector grades the switch itself: the shock detector built from the time derivative of div v, the alphaloc limiter and the decay of the per-particle alpha towards its minimum. `run.sh <ic>` builds the pinned source in a scratch copy and runs it, then copies the graded file into `OUT_DIR`. Configuration: Phantom's own unit-test binary: make SETUP=testkd (build/Makefile_setups) phantomtest, built SYSTEM=gfortran OPENMP=yes, then bin/phantomtest derivscd on SAB_THREADS=2 threads. run.sh copies only the lines that carry a result (' checking ...', '--> SKIPPING ...', 'PASSED: n of m', 'FAILED: ...', 'TEST SUITE PASSED/FAILED') into OUT_DIR/results.txt, dropping the banner, the host and thread count, the memory report, the timing lines and the randomly chosen epigraph, and it fails the run if no assertion line was printed or if no 'PASSED: n of m' line with n > 0 was printed. The suite reports one subtest and seven assertions.

Graded window: the whole upstream suite for this selector; nothing is shortened, and the suite is one upstream procedure that cannot be subdivided. SAB_SELECTORS can name a different selector for iteration, but a selector that matches nothing makes phantomtest fall through to the entire test suite. Runtime knobs, listed by `run.sh --help`: `SAB_SELECTORS` (the suite to run; the graded default is the single selector in `ic/<ic>/selectors.txt`) and `SAB_THREADS`; the defaults are the graded values. Measured on the authoring host (Apple M1 Ultra, gfortran 15.2, SYSTEM=gfortran OPENMP=yes, OMP_NUM_THREADS=2, three checks running at once): 14 s of graded run time (the calibration run on the remote host measured 5.6 s, which `expected_runtime_s` records rounded to 6 s) after 178 s of serial source build, which `run.sh` reports on stdout as `SAB_BUILD_SECONDS` and which the suite budget does not count.

## The two initial conditions

`ic/nominal/` holds the graded inputs described above. identical: the calibration run produced byte-identical nominal and variant outputs, which is the expected result here and not a defect - the two-ulp perturbation of a binary64 initial-condition literal is far below the four significant digits the es10.3 edit descriptor prints, so it cannot move the graded text; no coarser perturbation is invented, because a perturbation large enough to move the printed digits would no longer measure the round-off floor. ic/variant/source.patch raises rhozero, the uniform density the derivatives suites build their test particle distribution from (src/tests/test_derivs.f90:28), by two ulps of binary64: the literal 5.0 becomes 5.0000000000000018, a relative change of about 4.4e-16. The suite's inputs are literals in src/tests/test_derivs.f90, so a unified diff applied to the copy of the tree before the build is the only way to express an initial condition here; ic/nominal/source.patch is empty and ic/<ic>/selectors.txt names the single suite to run. The graded numbers are printed with the es10.3 edit descriptor, four significant digits (src/tests/utils_testsuite.f90:305, :340 and :926), so a two-ulp perturbation is at or below the printed resolution and the two runs are expected to print the same or almost the same text; the bound is therefore set from the printed precision, not from the variant, and is stated as such.

## The pass policy

The graded observable is the assertion text bin/phantomtest prints for the 'derivscd' suite: the same sequence of result lines with the same names and the same verdicts, the same 'PASSED: n of m' summary, and every number on those lines within |candidate - reference| <= 1e-12 + 0.002|reference|. What the check exercises: The upstream unit test of the Cullen and Dehnen (2010) artificial-viscosity switch (the selector is also spelled 'derivcullendehnen' and 'derivsswitch' in src/tests/testsuite.F90): on a uniform periodic lattice of test particles the suite calls the production derivative path src/main/deriv.F90, which runs the density loop of src/main/densityforce.F90 and the force loop of src/main/force.F90, and compares the result against analytic or independently summed values, printing a max error and the in-code tolerance for each assertion. SETUP=testkd (PERIODIC, IND_TIMESTEPS, CONST_ARTRES) is the build the survey measured as exercising about twice the number of subtests that SETUP=test does for these selectors, because the individual-timestep code paths are compiled in. This selector grades the switch itself: the shock detector built from the time derivative of div v, the alphaloc limiter and the decay of the per-particle alpha towards its minimum. The bound is physical because a port that mis-evaluates the div v time derivative, drops the limiter, or lets alpha decay at the wrong rate leaves the switch on in smooth flow or off in a shock, which moves the printed max error out of its fourth digit or turns an OK into a FAILED. It is achievable because the suite writes every error with the es10.3 edit descriptor, four significant digits (src/tests/utils_testsuite.f90:305, :340 and :926), so the smallest difference the graded text can express is one unit in the fourth digit, between 1.0e-04 and 1.0e-03 relative; the relative term is two units of that last printed digit and the absolute term keeps the integer counts on the 'PASSED: n of m' and 'FAILED on n of m' lines exact while allowing the handful of printed errors that are pure round-off, of order 1e-16, to move by their own magnitude. A difference below the printed resolution cannot move the text at all, which is why this check's floor is exact or near-exact agreement rather than a small number: the two runs printed byte-identical assertion text, so the measured spread is exactly zero over the 20 graded numbers. Calibration run 2026-09-02T13:50-14:42Z on the remote Docker host ale-worker (x86_64, Linux 6.17, 88 cpus, the check run under 16 cpus / 32 GB), record comment/pipeline/self-validation.json: reward 1.0, 13 of 13 passed, suite run time 396.2 s and 1203 s of source builds against a 900 s guidance budget. This check graded 20 numbers with a spread of 0 and the two outputs were byte-identical. The bound is left as authored and confirmed by the record: rtol 0.002 is two units of the last digit the es10.3 edit descriptor prints, which is what grades every number that carries physics, and atol 1e-12 is the floor that keeps the printed values which are pure round-off from being graded at their own magnitude. This suite prints no round-off-magnitude value at all: every max error on its seven assertion lines is exactly 0.000E+00, because the Cullen-Dehnen switch is compared against an analytic value that the lattice reproduces exactly. atol therefore never binds here; 1e-12 is carried for consistency with the rest of the family, and the two runs were byte-identical. On the lines whose in-code tolerance is tighter than atol - the near-exactness assertions - it is not the numeric bound that grades but the assertion verdict: validate.py requires the same line skeleton, the same OK/FAILED token and the same 'PASSED: n of m' counts, so any change that crosses upstream's own tolerance fails the check whatever atol is. How far a wrong port lands is argued from the suite's own hard-coded tolerances: 3.600E-04 on h, 1.000E-03 to 1.500E-03 on divv and curl v, 1.000E-05 on gradh and 3.500E-04 on alphaloc, the Cullen-Dehnen switch value itself. Every nominal max error is exactly zero, so a port whose switch differs at all moves a printed number from 0.000E+00 to a nonzero value; anything above 3.500E-04 also turns the alphaloc OK into a FAILED. The native fault probes of the same code path on the evolved checks (the artificial-conductivity switch removed from the Sedov check moves its graded arrays by 1.77e+02; the h-rho iteration tolerance loosened by a factor 100 (tolh 1e-04 -> 1e-02), the smallest plausible convergence fault, moves them by 1.02e-06 on the Kelvin-Helmholtz check and 1.80e-04 on the Sod check) show a real fault landing far beyond that. If a later run shows the printed digits moving further, the right response is to state the measured spread, not to widen the bound by hand.
